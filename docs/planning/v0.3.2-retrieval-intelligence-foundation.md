## Decision Summary

v0.3.2 adds a deterministic, taxonomy-aware retrieval package layer for future `indb ask`.

The new user entry point is:

```text
indb retrieve <query>
```

This phase does not generate answers. It builds auditable source evidence packages that future answer generation can consume.

Core invariants:

```text
Search retrieves source snippets.
Retrieve builds citation-ready source packages.
Ask is still not implemented.
Taxonomy may inform retrieval, but retrieval must not fix taxonomy.
Every retrieval item must bind to source doc, revision, chunk, and exact quote evidence.
```

## Confirmed Implementation Clarifications

These decisions were accepted before implementation planning and are part of the v0.3.2 contract.

### Public Surface

Add `indb retrieve <query>` as a new top-level command.

Do not rename or overload `indb search`. Ordinary search remains a current-source snippet search command with its existing `fts`, `vector`, and `hybrid` modes.

Add a read-only inspection command group for persisted packages:

```text
indb retrieval list
indb retrieval show <retrieval_run_id>
```

Do not make `retrieve` a command group that requires `indb retrieve run`.

### Persistence

`indb retrieve` persists retrieval packages by default.

The persisted package is audit data for future generated outputs. It must not be treated as:

- a citation record
- an output artifact
- a source revision
- a search index entry

Do not write ordinary `citations` rows from `retrieve`. The existing `citations` table remains reserved for generated artifacts.

### Intelligence Source

v0.3.2 uses a deterministic planner only.

Do not call a real LLM provider. Do not require API keys, auth, network, or remote services. Do not add new provider dependencies.

The existing fake-provider LLM harness may remain in the codebase for taxonomy tests, but v0.3.2 retrieval planning does not depend on model output.

### Signals

`retrieve` may consume:

- active categories
- active managed tags
- active accepted document tag assignments
- active document profiles
- active feature atoms from current source revisions

`retrieve` must ignore:

- pending taxonomy suggestions
- pending tag candidates
- stale profiles
- stale feature atoms
- archived documents
- source shells
- non-current source chunks at run time

### Filter And Boost Policy

Natural language taxonomy matches are soft boosts and explanation reasons only.

Hard filters require explicit query syntax such as:

```text
tag:<name-or-id>
category:<name-or-id>
```

Explicit filters must resolve to active formal taxonomy objects. Ambiguous, missing, deprecated, blocked, archived, or merged filters fail visibly instead of silently widening or narrowing the result set.

### Evidence Unit

The retrieval package item unit is `chunk + quote`.

Each item must store:

- `doc_id`
- `revision_id`
- `chunk_id`
- exact quote or quote window from the source chunk
- snippet
- source path
- base score
- taxonomy boost score
- final score
- match source
- deterministic reasons

The quote must be an exact substring of `chunks.text` for the referenced chunk. Snippets may be rendered for readability, but snippets are not enough to satisfy the evidence contract.

### Candidate Generation

Default candidate generation uses existing hybrid search:

```text
fts + CJK fallback + deterministic vector
```

v0.3.2 does not add real embeddings, real vector providers, remote rerankers, or query expansion providers.

Users may still choose `--mode fts`, `--mode vector`, or `--mode hybrid`.

### Profile Behavior

`retrieve` does not auto-build missing profiles.

If a candidate document has no active current profile, the retrieval package may still include it through base search. The run should record a warning or reason such as `profile_missing`, and the CLI should point users to explicit profile/taxonomy preparation commands.

Allowed follow-up commands remain explicit:

```text
indb profile build <doc_id>
indb taxonomy analyze <doc_id>
```

### Diversity

By default, `retrieve` limits package diversity by document.

Default:

```text
per_doc_limit = 3
```

Expose:

```text
--per-doc-limit <n>
```

This prevents one long document from filling the entire evidence package. A value less than one is invalid.

### Release Gate

v0.3.2 has a deterministic release gate.

Real-corpus dogfood is recommended, but it is not the hard release blocker for the first v0.3.2 implementation.

## Goals

- Add a retrieval package layer between raw search and future answer generation.
- Make retrieval packages durable, inspectable, and doctor-auditable.
- Use v0.3.1 taxonomy/profile signals for explainable ranking without letting pending taxonomy affect results.
- Preserve exact source binding for every retrieved evidence item.
- Keep all behavior local-first, deterministic, and testable.
- Keep ordinary `indb search` behavior unchanged.

## Non-goals

- Do not implement `indb ask`.
- Do not generate answers, summaries, cards, or claims.
- Do not write generated-artifact citations.
- Do not write output files or output artifacts.
- Do not mutate source Markdown, revisions, chunks, originals, source files, tags, aliases, categories, or profiles.
- Do not automatically build profiles or run taxonomy analysis.
- Do not use pending suggestions or candidates for ranking.
- Do not add real LLM providers, external rerankers, or network model calls.
- Do not change default `indb search` ranking.

## Ownership Boundary

indbase owns:

- retrieval schema
- deterministic query parsing
- deterministic planner output
- candidate generation through existing search service
- taxonomy/profile boost calculation
- diversity limiting
- persisted retrieval runs and items
- CLI rendering
- doctor checks

Retrieval may read:

- current source documents and chunks
- accepted category and tag state
- active document profiles
- active feature atoms
- existing search results returned by the search service

Retrieval must not write:

- source Markdown files
- document revisions
- chunks
- source files
- originals
- output artifacts
- `citations`
- formal taxonomy mutations
- profiles or feature atoms

## Schema Plan

Use a new migration after v0.3.1 taxonomy foundation.

### `retrieval_runs`

```sql
CREATE TABLE retrieval_runs (
  retrieval_run_id TEXT PRIMARY KEY,
  query_text TEXT NOT NULL,
  normalized_query_text TEXT NOT NULL,
  planner_version TEXT NOT NULL,
  base_mode TEXT NOT NULL,
  linked_search_query_id TEXT,
  filters_json TEXT NOT NULL,
  planner_json TEXT NOT NULL,
  warnings_json TEXT NOT NULL,
  top_k INTEGER NOT NULL,
  candidate_k INTEGER NOT NULL,
  per_doc_limit INTEGER NOT NULL,
  result_count INTEGER NOT NULL,
  status TEXT NOT NULL,
  created_at TEXT NOT NULL,
  finished_at TEXT,
  FOREIGN KEY(linked_search_query_id) REFERENCES search_queries(query_id)
);
```

Valid `status` values:

```text
succeeded
failed
partial
```

Rules:

- `query_text` preserves user input.
- `normalized_query_text` is the planner input after stripping explicit filters.
- `filters_json` stores resolved explicit filters.
- `planner_json` stores deterministic planner terms, boost signals, and versions.
- `warnings_json` stores non-fatal issues such as missing profiles.
- A failed run may exist with zero items if parsing or resolution fails after the run starts.

### `retrieval_items`

```sql
CREATE TABLE retrieval_items (
  retrieval_item_id TEXT PRIMARY KEY,
  retrieval_run_id TEXT NOT NULL,
  rank INTEGER NOT NULL,
  doc_id TEXT NOT NULL,
  revision_id TEXT NOT NULL,
  chunk_id TEXT NOT NULL,
  title TEXT,
  source_path TEXT,
  quote TEXT NOT NULL,
  snippet TEXT NOT NULL,
  base_score REAL NOT NULL,
  taxonomy_score REAL NOT NULL,
  final_score REAL NOT NULL,
  match_source TEXT NOT NULL,
  reasons_json TEXT NOT NULL,
  created_at TEXT NOT NULL,
  FOREIGN KEY(retrieval_run_id) REFERENCES retrieval_runs(retrieval_run_id),
  FOREIGN KEY(doc_id) REFERENCES documents(doc_id),
  FOREIGN KEY(revision_id) REFERENCES document_revisions(revision_id),
  FOREIGN KEY(chunk_id) REFERENCES chunks(chunk_id)
);
```

Rules:

- `quote` must be an exact substring of the referenced chunk text.
- `rank` is final package rank after filtering, reranking, and diversity limiting.
- `reasons_json` must be deterministic and explainable.
- Items may continue to reference historical revisions after a later re-ingest. Historical packages remain valid as audit records as long as referenced rows and source files still exist.

Suggested ID prefixes:

```text
retrrun_...
retritem_...
```

## Core Flow

### Retrieve Run

```text
indb retrieve <query>
  -> parse explicit filters
  -> resolve tag/category filters against active formal taxonomy
  -> create retrieval run
  -> call existing search service with candidate_k and base mode
  -> load candidate chunks, documents, categories, tags, profiles, feature atoms
  -> apply hard filters
  -> apply deterministic taxonomy/profile boosts
  -> extract exact quote windows from chunks
  -> apply per-document diversity limit
  -> persist retrieval items
  -> finish retrieval run
  -> render package summary
```

Failure rules:

- empty query after removing filters fails
- invalid mode fails
- ambiguous explicit tag/category filter fails
- unresolved explicit tag/category filter fails
- invalid `top_k`, `candidate_k`, or `per_doc_limit` fails
- quote extraction failure fails the affected item; if no valid items remain, run status is `failed`

### Query Parsing

Supported explicit filters:

```text
tag:<tag-id-or-name-or-alias>
category:<category-id-or-name>
```

Rules:

- Filters are removed from `normalized_query_text`.
- Repeated filters of the same kind are allowed only if semantics are explicit and deterministic.
- v0.3.2 should use AND semantics for multiple explicit filters of the same kind.
- Ambiguous names must ask the user to use IDs; they must not pick a winner silently.
- Free text terms may still soft-match taxonomy names and aliases for boosts.

### Ranking

Ranking starts from the existing search candidate order and score.

Allowed deterministic boosts:

- current document category matches explicit or inferred category term
- active document tag matches explicit or inferred tag term
- active feature atom text or normalized text matches query terms
- exact taxonomy name or alias match in query

Rules:

- Boosts must be bounded so base relevance remains visible.
- Every non-zero boost must add a reason.
- Pending suggestions and candidates add no boost.
- Missing profile is a warning/reason, not a failure.

### Quote Extraction

Quote extraction must prefer an exact source substring around the strongest evidence term.

Fallback order:

1. explicit taxonomy or feature evidence quote when it belongs to the same chunk and is an exact substring
2. query term window in chunk text
3. beginning window of chunk text

If no non-empty exact quote can be produced, do not persist the item.

## CLI Scope

Add:

```text
indb retrieve <query>
indb retrieval list
indb retrieval show <retrieval_run_id>
```

`indb retrieve` options:

```text
--vault <path>
--top-k <n>
--candidate-k <n>
--mode fts|vector|hybrid
--per-doc-limit <n>
--json
```

Default values:

```text
top_k = existing search config top_k unless overridden
candidate_k = max(top_k * 5, 25)
mode = hybrid
per_doc_limit = 3
```

Human output should show:

- retrieval run id
- normalized query
- filters
- warnings
- ranked items
- doc/revision/chunk ids
- quote
- reasons

JSON output should include full run and item data.

Do not add TUI workflows in v0.3.2 unless explicitly requested after the CLI path is stable.

retrieval_run_invalid_json

Rules:

- Doctor must not repair retrieval records.
- Doctor must not rerun retrieval.
- Doctor must not call LLMs.
- Historical retrieval items may reference old revisions and old chunks; that is valid if those rows still exist and the quote matches the chunk text.

## Acceptance Checklist

- `indb retrieve` persists an inspectable retrieval package by default.
- `indb retrieval list/show` can read packages back.
- Each item has doc, revision, chunk, quote, snippet, scores, match source, and reasons.
- Every quote is an exact substring of the referenced chunk.
- Explicit `tag:` and `category:` filters are deterministic and fail visibly on ambiguity.
- Natural language taxonomy matches only boost; they do not hard-filter.
- Pending taxonomy artifacts do not affect retrieval.
- Missing profiles do not trigger implicit profile builds.
- Default per-document diversity limit is enforced.
- Ordinary `indb search` behavior and ranking are unchanged.
- No `citations`, source revisions, chunks, output artifacts, or taxonomy mutations are written by retrieval.
- Doctor reports corrupt retrieval records.
- Deterministic v0.3.2 gate passes.
