## Decision Summary

v0.3.1 builds the governed taxonomy layer that later intelligent retrieval will consume. It does not implement `indb ask`, answer generation, `search-smart`, retrieval planning, or ranking changes.

The phase is named **Taxonomy Foundation** because the main deliverable is controlled directory and tag infrastructure:

```text
LLM extracts meaning.
Manager governs meaning.
Search consumes governed meaning.
Doctor audits meaning.
User reviews high-risk meaning.
```

In this document, **directory** means indbase's L1 category layer. It does not mean the vault filesystem layout, source Markdown paths, originals, or revision storage.

Core invariants:

```text
L1 categories are controlled.
L2 managed tags are typed and governed.
L3 feature atoms are open but evidence-bound.
LLM output is suggestion data only.
Formal taxonomy mutations require manager rules or user acceptance.
Search behavior is not changed in v0.3.1.
```

## Confirmed Implementation Clarifications

These clarifications were accepted during implementation review and should guide the first v0.3.1 build.

### Delivery Slices

Implement v0.3.1 in small release slices:

1. Schema, legacy backfill, service validation, and doctor hard checks.
2. Deterministic profiles, feature atoms, and tag candidate manager.
3. Review/accept flows, category manager, FTS metadata refresh after accepted mutations, and janitor V1.
4. Fake-provider LLM harness, model-call records, schema rejection tests, and gate scripts.

Do not attempt the full 13-step plan as one large change.

### Legacy Backfill

Existing tags must be migrated into the typed tag model deterministically:

- `ai` -> `topic`
- `rag` -> `method`
- `embedding` -> `method`
- `ocr` -> `method`
- `sqlite` -> `tool`
- `python` -> `tool`
- any other existing active tag -> `topic`

Backfilled tags use `status = active` and `created_by = legacy_migration`. Janitor or doctor may later surface legacy type review risks, but migration must not leave untyped tags.

Existing document categories need light provenance:

```text
category_source
category_suggestion_id
category_updated_by
category_updated_at
```

Backfill `category_source` as `system_seed` for empty or `cat_uncategorized` values, and `manual_legacy` for any other existing category assignment. Manual category overwrite protection remains conservative: any non-empty, non-uncategorized category requires explicit force to replace through suggestion acceptance.

### Schema Constraint Policy

New taxonomy tables should use SQLite constraints for allowed types, statuses, sources, confidence bounds, and foreign keys where practical. Existing tables should be hardened conservatively with additive columns, service-layer validation, and doctor checks rather than risky table rebuilds unless a rebuild is explicitly justified.

Use partial or service-layer deduplication for active profiles, active-ish tag candidates, and repeated taxonomy suggestions. Do not rely on database errors as the user-facing validation path.

New taxonomy IDs use these prefixes:

```text
profile_...
feat_...
tagcand_...
taxsugg_...
tagevent_...
modelcall_...
```

### Tags, Aliases, And Assignments

All new formal tag creation must provide an explicit allowed type. `indb tag add <name>` must not silently default to `topic` after v0.3.1 migration. Candidate promotion defaults to the candidate type, but a human promotion command may explicitly override the type; this override must be recorded in candidate and lifecycle payloads.

`tag_aliases` needs its own status model:

```text
active
deprecated
blocked
```

`normalized_alias` remains globally unique. Deprecated or blocked aliases do not participate in matching, but they must block accidental recreation until an explicit restore, unblock, merge, or equivalent review action occurs.

Keep `document_tags` as the current assignment table with primary key `(doc_id, tag_id)`. v0.3.1 adds provenance fields but does not introduce assignment history rows. If an assignment is restored, update the existing row provenance. Future full assignment history can use a separate event table if needed.

### Suggestions And Review

`taxonomy_suggestions` is the canonical table for new v0.3.1 governance flows. Keep `classification_suggestions` for compatibility and historical reads, but new profile, tag, category, janitor, and LLM-governed flows should write `taxonomy_suggestions`.

Legacy `classify accept` behavior must be tightened: accepting suggested tags must not create formal new tags directly. Missing tags should become `tag_candidates` or taxonomy review objects.

`review_items` remain a generic queue entry only. Generic review resolution must not perform taxonomy mutations. Business mutations happen through dedicated commands such as suggestion accept/reject, candidate promote/reject, alias add, merge, archive, or deprecate. Successful dedicated commands should resolve related review items.

Revision binding depends on suggestion type:

- `category_assign`, `tag_assign`, and document-derived `tag_candidate` suggestions require `doc_id` and `revision_id`, and become stale when the document current revision changes.
- Global janitor suggestions such as `tag_merge`, `tag_deprecate`, and `tag_archive` do not require a revision.
- `alias_add` may be document-bound when derived from evidence, or global when emitted by janitor.

### Profiles And Feature Atoms

Profile building is an explicit downstream operation in v0.3.1. Do not run profile extraction automatically inside ingest or re-ingest. Ingest remains responsible for source, revision, chunk, and index state. Profile commands and gates may build profiles later.

Source shell means a document with no current source revision. Profile, category suggestion, tag suggestion, and feature extraction flows must reject documents where `current_revision_id IS NULL`, `ingest_status != 'revisioned'`, or no current chunks exist.

Deterministic profile V1 writes a digest for classification, not a generated summary. `summary_for_classification` should contain traceable material such as title, top headings, source type, language, and top feature texts. It must not synthesize a natural-language summary.

Feature extraction V1 should stay intentionally narrow:

- use title, heading path, chunk text, known tag names, and known aliases
- extract conservative English 2-4 word phrases
- for CJK, prefer known tag/alias exact occurrences and conservative phrase windows
- avoid fenced code, pure URLs, very short tokens, and stopwords
- limit to Top 5 features per chunk and Top 30 per document
- no third-party NLP dependency

For deterministic features, `quote` must be an exact source substring from the referenced chunk. LLM-origin features must also pass quote evidence validation. Model rationale must never be stored as quote evidence.

### Tag Manager And Candidates

Fuzzy matching V1 uses only the Python standard library, such as `difflib.SequenceMatcher` plus normalized token overlap. Exact tag name and alias matches run first. Fuzzy matching compares only within the same tag type.

Candidate deduplication is status-aware for the same `normalized_name + type`:

- `pending`: merge new evidence and counts.
- `accepted`: resolve toward the promoted tag path.
- `rejected`: do not recreate by default; append observation or create a low-priority reobserved review.
- `blocked`: never recreate; return a blocked conflict.
- `merged`: route toward the target tag or alias path.
- `archived`: do not automatically reopen; create a review suggestion if needed.

Automatic promotion remains disabled in v0.3.1 even if future thresholds are stored.

### Category Manager

Category manager V1 uses existing category fields and feedback only:

- `categories.name`
- `categories.description`
- `categories.include_rules`
- `categories.exclude_rules`
- accepted `classification_feedback`
- accepted `taxonomy_suggestions(category_assign)`
- existing M8 keyword fallback when no rules are present

Do not add a dedicated category examples table in v0.3.1.

### Search And FTS

Pending taxonomy artifacts must not affect search. Accepted formal category and document tag mutations may refresh existing FTS metadata using current indexer behavior. This is metadata consistency after an accepted mutation, not a new ranking or retrieval feature.

Do not index feature atoms, tag candidates, or pending suggestions into default source search.

### Janitor V1

Janitor V1 should be low-noise and deterministic. It should first catch obvious integrity and governance problems:

- normalized duplicate active tags
- alias collisions
- candidate conflicts with active tags or aliases
- promoted candidate without promoted tag
- assignment to deprecated, archived, blocked, or merged tags
- stale document-bound pending suggestions
- empty active categories
- low-frequency pending candidates only when `distinct_doc_count < 2` and age is over 30 days

Keep overbroad tag detection, category overload detection, and fuzzy merge suggestions as warnings or deferred work until real corpus behavior is understood.

### LLM Harness

v0.3.1 implements only the fake-provider harness contract. Do not add real provider dependencies, read API keys, or send network model calls in this phase.

The harness must still support model-call records, schema validation, invalid output rejection, timeout or failure recording, and evidence validation through fake-provider tests and gates. Deep doctor may smoke-test the fake provider only when explicitly requested.

## Goals

- Harden L1 category management as a low-cardinality controlled directory layer.
- Harden L2 managed tags with fixed tag types, aliases, lifecycle events, and assignment provenance.
- Add L3 feature atoms bound to current chunks with type, confidence, and quote evidence.
- Add document profiles bound to immutable revisions.
- Add tag candidates and taxonomy suggestions for review-first growth.
- Add deterministic profile and taxonomy manager flows before LLM use.
- Add CLI/TUI-oriented review commands for tag candidates, tag assignment suggestions, and category suggestions.
- Add taxonomy janitor audits that suggest cleanup without destructive mutation.
- Add doctor checks for taxonomy referential integrity and stale derived data.
- Activate LLM harness only for schema-validated suggestions; no direct taxonomy writes.

## Non-goals

- Do not implement `indb ask`.
- Do not generate answers, summaries, or facts for users.
- Do not implement `search-smart`, retrieval planner, retrieval packages, or query expansion in this phase.
- Do not change default search ranking or hybrid retrieval behavior.
- Do not let LLMs create, delete, rename, merge, or directly assign categories.
- Do not let LLMs directly write `document_tags`, `tags`, `tag_aliases`, or `documents.category_id`.
- Do not build a knowledge graph.
- Do not automatically create complex category trees.
- Do not allow unreviewed bulk category or tag mutation.

## Ownership Boundary

indbase owns:

- category registry
- tag registry, aliases, lifecycle, and assignment provenance
- document profiles
- feature atoms
- tag candidates
- taxonomy suggestions
- review records
- doctor checks
- final durable taxonomy mutations after acceptance

LLM providers may only produce:

- schema-validated taxonomy suggestions
- schema-validated tag arbitration decisions
- schema-validated category suggestion payloads
- model call records

LLM providers must not:

- write source Markdown
- write document revisions, chunks, source files, originals, or output artifacts
- directly mutate categories, tags, aliases, or document tag assignments
- bypass `indbase-llm-harness`
- generate answers for user queries

## Three-Tier Taxonomy Model

### L1 Category

Categories are the controlled top-level directory layer.

Purpose:

- path-style navigation
- coarse filtering
- statistics
- routing
- broad document grouping

Rules:

- Every document has at most one `primary_category` in v0.3.1.
- Secondary categories are deferred.
- Category count should remain small.
- Category changes are low-frequency.
- LLMs may only suggest an existing category.
- LLMs must not create, delete, merge, or rename categories.
- New categories can only be represented as review suggestions; formal creation is manual.
- Manual category assignments are protected from automatic overwrite.
- If a user has manually set a category, future category changes require explicit forced acceptance.

Categories are not a knowledge graph and must not carry fine-grained semantics that belong in tags or feature atoms.

### L2 Managed Tags

Managed tags are formal business tags.

Purpose:

- precise filtering
- metadata indexing
- future retrieval boost signals
- aggregation and statistics
- stable user-facing vocabulary

Rules:

- Tags are not free strings.
- Every active tag must have one fixed type.
- v0.3.1 tag types are fixed and not user-extensible:

```text
topic
method
tool
entity
workflow
format
language
project
```

- New tags do not go directly into `tags`.
- New tags first enter `tag_candidates`.
- Formal tag promotion requires user acceptance in v0.3.1.
- Auto-promotion rules may be stored for future use but must default off.
- A candidate observed in only one document must not auto-promote.
- Deprecated or blocked aliases must prevent accidental re-creation.
- Tag aliases must be unique by normalized alias.
- Alias collisions are doctor findings.

Example managed tag:

```json
{
  "name": "hybrid-search",
  "type": "method",
  "aliases": ["hybrid retrieval", "mixed retrieval", "混合检索"]
}
```

### L3 Feature Atoms

Feature atoms are open, evidence-bound features extracted from documents and chunks.

Purpose:

- long-tail semantics
- tag candidate discovery
- local keyword fallback
- future query expansion inputs
- future vector or hybrid retrieval enrichment

Rules:

- Feature atoms are derived data, not formal tags.
- Feature atoms are revision-bound and stale when the source revision is no longer current.
- Every feature atom must bind to an existing chunk.
- Every feature atom must have a type.
- Every feature atom must have a confidence score.
- Every feature atom must have quote or evidence text from the source chunk.
- Every feature atom must have a source: `deterministic` or `llm`.
- Low-confidence feature atoms remain local keywords and do not enter tag candidate promotion flow.
- Feature atoms from old revisions do not participate in default current taxonomy operations.
- Feature atoms from archived documents do not participate in default current taxonomy operations.
- Keep two limits: per-chunk Top N features and per-document Top M features.

Example feature atom:

```json
{
  "text": "SQLite FTS",
  "normalized_text": "sqlite-fts",
  "type": "tool",
  "confidence": 0.94,
  "chunk_id": "chunk_rev_doc_20260520_ab12cd_0001_0001",
  "quote": "SQLite FTS indexes current source chunks..."
}
```

## Modules

### `indbase-profile`

Builds document profiles.

Inputs:

- `doc_id`
- current `revision_id`
- title
- language
- source type
- current chunks
- headings
- existing category and tags

Outputs:

- `document_profiles`
- optionally `feature_atoms`

Version 1 must be deterministic:

- title and headings
- current chunk text
- simple keyword and phrase extraction
- existing category and tag context
- no provider calls

Version 2 may use LLMs through `indbase-llm-harness`, but only after the deterministic profile contract and doctor checks are stable.

### `indbase-taxonomy-manager`

Maps L3 feature atoms toward L2 managed tags.

Flow:

```text
feature atom
  -> normalized exact tag match
  -> alias exact match
  -> lexical fuzzy match
  -> optional embedding similarity when available
  -> optional LLM arbitration for ambiguous cases
  -> existing tag assignment suggestion / ambiguous / tag candidate / local keyword
```

Threshold policy:

```text
score >= 0.90
  direct high-confidence existing tag suggestion

0.75 <= score < 0.90
  tag assignment suggestion requiring review

0.55 <= score < 0.75
  ambiguous review

score < 0.55
  pending tag candidate or local keyword
```

v0.3.1 must not auto-write formal `document_tags` from LLM decisions. It may create deterministic high-confidence suggestions for CLI/TUI review.

### `indbase-category-manager`

Suggests document categories from profiles and existing category registry.

Rules:

- Only existing categories can be suggested.
- New category creation is out of scope for automatic flows.
- Category suggestions should use category descriptions, include rules, exclude rules, and accepted examples.
- Auto-apply is not enabled in v0.3.1.
- Future low-risk auto-apply may be limited to uncategorized documents with very high confidence and no strong alternative.
- Manual category overwrites require explicit force acceptance.

### `indbase-taxonomy-janitor`

Runs background or explicit audits. It must not block ingest.

Responsibilities:

- duplicate tag audit
- alias collision audit
- alias suggestion
- tag merge suggestion
- low-frequency tag candidate warning
- stale pending tag candidate warning
- overbroad tag detection
- category overload detection
- empty category detection

Janitor may suggest:

- add alias
- merge tags
- deprecate tag
- archive tag
- promote tag candidate
- block overbroad tag candidate

Janitor must not:

- physically delete tags
- bulk merge tags automatically
- overwrite `document_tags`
- create categories
- change source documents or revisions

### `indbase-llm-harness`

All LLM calls must go through this harness.

Responsibilities:

- provider config
- prompt registry
- schema validation
- model call records
- timeout and retry policy
- failure behavior
- token and cost logging when available
- output validation
- evidence validation

v0.3.1 enables LLMs only for suggestions and arbitration:

- feature-to-tag arbitration
- category suggestion

LLM outputs must never mutate formal taxonomy directly.

### `indbase-intelligence-gates`

Adds deterministic release gates for taxonomy data quality.

Suggested scripts:

```text
n1_taxonomy_schema_gate.py
n2_profile_feature_gate.py
n3_tag_candidate_manager_gate.py
n4_category_manager_gate.py
n5_taxonomy_janitor_gate.py
n6_llm_harness_suggestion_gate.py
```

These gates should remain separate from future retrieval gates.

## Core Flows

### Profile Build Flow

```text
indb profile build <doc_id>
  -> verify document exists
  -> verify document is active
  -> reject source shell
  -> verify current_revision_id exists
  -> load current chunks
  -> extract deterministic profile summary
  -> extract feature atoms
  -> validate every feature has chunk/type/confidence/quote
  -> write document_profiles
  -> write feature_atoms
  -> mark old profiles/features stale for prior current revision when needed
```

Failure rules:

- missing current revision -> fail
- source shell -> fail
- no chunks -> fail
- archived document -> fail by default
- feature without chunk -> reject feature
- feature without quote -> reject feature
- invalid feature type -> reject feature

### Tag Manager Flow

```text
active feature atoms
  -> exact managed tag match
  -> alias match
  -> fuzzy lexical match
  -> optional vector similarity
  -> optional LLM arbitration
  -> taxonomy_suggestions / tag_candidates / local_keyword status
```

New tag promotion rules for future automation:

```text
occurrence_count >= 3
distinct_doc_count >= 3
evidence_chunks >= 3
no active tag similarity > 0.75
no blocked or deprecated alias conflict
```

v0.3.1 rule:

- Automatic promotion is disabled.
- User can manually promote a candidate.
- Single-document candidates cannot auto-promote.

### Category Manager Flow

```text
document profile
  -> load active category registry
  -> load accepted examples and feedback
  -> rank existing categories
  -> create category_assign suggestion
  -> validate suggested category exists
  -> write review item
```

Rules:

- No new category creation.
- No automatic overwrite of manual category.
- Force is required for explicit manual overwrite.
- Suggestions for old revisions become stale after re-ingest.

### Taxonomy Janitor Flow

```text
indb taxonomy audit
  -> load active categories, tags, aliases, candidates, assignments
  -> find normalized duplicate tags
  -> find alias collisions
  -> find fuzzy merge candidates
  -> find low-frequency candidates
  -> find overbroad active tags
  -> find stale pending suggestions
  -> emit findings and suggestions
```

Janitor suggestions use `taxonomy_suggestions` and review items. Janitor must not bulk mutate formal taxonomy by itself.

### LLM Suggestion Flow

```text
input object
  -> manager builds small evidence context
  -> indbase-llm-harness call
  -> schema validation
  -> evidence validation
  -> taxonomy_suggestions or tag_candidates
  -> review item
```

LLM failure behavior:

- invalid schema -> reject output and record error
- timeout -> record model call failure and task error
- missing evidence -> reject output
- suggested unknown category -> reject output
- direct mutation attempt -> impossible by API boundary

## LLM Strategy

### Step 1: No-LLM Taxonomy Manager

Build first:

- deterministic profile builder
- deterministic feature extraction
- normalized tag exact match
- alias match
- fuzzy match
- tag candidate creation
- category suggestion from deterministic profile and category examples

Goal: prove governance model without model variance.

### Step 2: LLM Arbitration

Use LLMs only for gray zones:

- Is this feature an alias of an existing tag?
- Is this feature a new tag candidate?
- Is this feature too specific and only a local keyword?
- Which existing category best fits this document?

Input should be small:

- one feature atom or one document profile
- top similar tags or categories
- aliases
- evidence quotes
- current category context

Output schema example:

```json
{
  "decision": "alias_to_existing",
  "tag_id": "tag_sqlite_fts",
  "candidate_name": null,
  "confidence": 0.82,
  "reason": "The quoted evidence uses SQLite FTS as a tool name.",
  "evidence_chunk_ids": ["chunk_rev_doc_20260520_ab12cd_0001_0001"]
}
```

Allowed decisions:

```text
alias_to_existing
new_tag_candidate
local_keyword
ambiguous
category_assign
no_category
```

### Step 3: Retrieval Intelligence

Deferred. Do not implement in v0.3.1.

Future retrieval work may consume:

- active categories
- active managed tags
- active accepted document tag assignments
- current feature atoms
- accepted feedback

It must not become responsible for fixing taxonomy.

## Acceptance Checklist

- Category suggestions only target existing categories.
- Managed tags have fixed types.
- Feature atoms are chunk-bound, evidence-bound, typed, and confidence-scored.
- Document profiles are revision-bound and stale correctly.
- Tag candidates carry evidence and do not pollute formal tags.
- Document tag assignments have provenance.
- Manual category assignments are protected.
- Janitor produces suggestions without physical deletes or bulk mutation.
- LLM calls go through harness and write suggestions only.
- Doctor reports missing, stale, invalid, or dangling taxonomy records.
- Existing ingest, output, revision, chunk, FTS, and search invariants remain unchanged.
