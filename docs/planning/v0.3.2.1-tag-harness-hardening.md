## Decision Summary

v0.3.2.1 hardens the tag harness after v0.3.2 Tag Governance Foundation.

This phase makes governed tag behavior measurable, regression-testable, feedback-aware, and hard to regress. It does not replace the existing v0.3.3 retrieval evaluation / answer readiness phase.

Primary contract:

```text
fixture cases -> isolated eval vault -> deterministic tag governance run
-> exact expectation checks -> stable summary/artifacts -> CI gate
```

Core invariants:

```text
Wrong trusted tag metadata is a release blocker.
Harness may report and suggest, but must not mutate production tag policy.
Harness runs are deterministic, local, schema-neutral by default, and isolated from user vaults.
```

## Goals

- Define an explicit tag harness case schema.
- Add a sanitized fixture suite under `tests/fixtures/v0321_tag_harness/`.
- Create isolated eval vaults for harness execution.
- Seed trusted current-revision documents, chunks, FTS, tags, aliases, lifecycle, scope, blocklist, manual tags, and feedback-derived cases through core services where possible.
- Evaluate tag behavior at case, candidate, document, and run levels.
- Produce stable machine-readable summary JSON.
- Produce local diagnostic artifacts with minimal reproduction details for each failure.
- Add zero-tolerance hard gates for dangerous tag governance regressions.
- Add report-only metrics for candidate precision/recall and quantity pressure.
- Add a release gate script and CI job after the local gate passes.
- Update testing/project-status docs after implementation and verification.

## Non-goals

- Do not add a formal user-facing `indb tag harness` command in this phase.
- Do not add production vault schema or migrations by default.
- Do not write harness run history into a user's production vault by default.
- Do not call LLM providers, embedding providers, network services, or read API keys.
- Do not implement search ranking, hybrid search, query expansion, retrieval packages, or `ask`.
- Do not automatically mutate tag policy, aliases, merges, scopes, blocklists, budgets, or applied tags.
- Do not commit raw private vault content or unsanitized feedback exports.
- Do not retest swallow conversion, transition export, OCR, PDF ingest, or provider behavior.
- Do not rewrite core tag governance semantics unless a harness case exposes a real defect.
- Do not replace doctor with harness or harness with doctor.

## Case Schema

Add fixture data under:

```text
tests/fixtures/v0321_tag_harness/
  cases.jsonl
  README.md
```

Each JSONL row is one explicit expected-outcome case. Required fields:

```json
{
  "case_id": "taghcase_active_canonical_auto_attach",
  "source": "synthetic",
  "title": "SQLite storage note",
  "content": "We use sqlite for local-first storage.",
  "seed_tags": [],
  "manual_tags": [],
  "raw_candidates": [],
  "expected_auto_attached": [],
  "expected_candidates": [],
  "expected_blocked": [],
  "expected_search_hits": [],
  "expected_warnings": []
}
```

Recommended optional fields:

```json
{
  "category_id": "cat_systems",
  "seed_aliases": [{"tag": "rag", "alias": "retrieval augmented generation", "language": "en"}],
  "seed_lifecycle": [{"tag": "old-rag", "status": "merged", "merged_into": "rag"}],
  "seed_blocklist": [{"pattern": "misc", "match_type": "exact", "reason": "low value"}],
  "seed_scopes": [{"tag": "sqlite", "scope": "category_bound", "category_id": "cat_systems"}],
  "seed_feedback": [],
  "expected_failures": [],
  "expected_reason_codes": [],
  "notes": "Why this case exists."
}
```

Rules:

- Expected outcomes must be explicit.
- Harness must not infer expectations from case names or prose.
- Fixtures committed to the repo must be synthetic or sanitized.
- Feedback-derived fixtures must carry a sanitized source marker such as `feedback_derived_sanitized`.
- Unsupported keys should fail fixture validation unless explicitly allowed.
- Fixture load order must be deterministic.

## Minimum Coverage Matrix

The first fixture suite must cover:

- existing active canonical tag can be safely auto-attached
- user-added active canonical tag can be safely auto-attached
- English alias resolves to the canonical tag
- Chinese or multilingual alias resolves to the same canonical tag
- deprecated tag is not auto-attached
- merged tag is not auto-attached as the old tag and resolves for search when appropriate
- archived tag is not auto-attached and is excluded from trusted filtering
- blocklist rejects low-value raw candidates
- over-specific/path/date/version-like/vague/category-equivalent new-tag proposals are blocked or rejected
- manual tags are not deleted, overwritten, or silently replaced
- category-bound scope prevents cross-category auto-attach
- candidate tags do not enter trusted tag search filters
- relation-backed tag search returns expected source text for trusted tags
- alias-to-canonical tag search returns the same trusted document set
- rejected/blocked candidates do not pollute trusted filters
- feedback-derived accept/reject/merge/block cases can become stable sanitized regression cases
- quantity control reports candidate counts, new-tag proposals, near-budget pressure, and sprawl reasons

## Eval Vault Seeding

The harness must use an isolated eval vault by default:

```text
temporary root -> init_vault -> seed cases -> run harness -> emit summary/artifacts
```

Seed documents represent already trusted source state:

- active `documents` row
- current `document_revisions` row
- source Markdown file in `sources/`
- current `chunks`
- FTS state

Rules:

- Do not invoke real swallow conversion.
- Do not invoke transition export.
- Do not use OCR/PDF/network/provider fixtures.
- Use existing core helpers where available.
- If direct DB seeding is unavoidable for fixture setup, keep it inside test/harness helper code and do not expose it as production behavior.
- Default execution must not touch a user's production vault.

## Evaluation Layers

Evaluate at four layers:

### Case layer

The smallest reproducible unit.

Checks:

- fixture validates against schema
- seeded state matches case setup
- expected outcomes are explicit
- sanitized source marker is present when needed

### Candidate layer

Checks:

- raw candidates pass Tag Resolution before persistence
- candidate type matches expectation
- attach-existing candidates point to canonical tags
- new-tag proposals pass admission and budget before review
- blocked candidates carry reason codes
- deprecated/merged/archived states cannot become auto-attach

### Document layer

Checks:

- expected auto-attached tags match exactly
- forbidden auto-attached tags are absent
- manual tags are preserved
- candidate count stays within per-document budget
- expected warnings match
- evidence points to the current revision/chunk state

### Run layer

Checks:

- aggregate dangerous failures are zero
- per-run candidate and new-tag proposal budgets are respected
- trusted tag filter is not polluted
- policy state is unchanged by harness execution
- summary and artifact files are stable and machine-readable
- doctor hard findings are zero for the healthy eval vault

## Summary Contract

The release gate reads a stable JSON summary. Suggested top-level shape:

```json
{
  "phase": "v0.3.2.1",
  "status": "passed",
  "case_count": 0,
  "passed_case_count": 0,
  "failed_case_count": 0,
  "hard_gates": {
    "wrong_auto_attached_tags": 0,
    "manual_tag_mutations": 0,
    "trusted_filter_pollution": 0,
    "deprecated_merged_archived_auto_attach": 0,
    "unresolved_candidate_persisted": 0,
    "budget_violations": 0,
    "policy_mutations_by_harness": 0
  },
  "report_metrics": {
    "candidate_precision": null,
    "candidate_recall": null,
    "candidate_count_by_doc": {},
    "new_tag_proposals_by_run": 0,
    "blocked_sprawl_candidates": 0,
    "near_budget_docs": [],
    "top_sprawl_reasons": []
  },
  "failures": []
}
```

Hard gate rules:

- `wrong_auto_attached_tags = 0`
- `manual_tag_mutations = 0`
- `trusted_filter_pollution = 0`
- `deprecated_merged_archived_auto_attach = 0`
- `unresolved_candidate_persisted = 0`
- `budget_violations = 0`
- `policy_mutations_by_harness = 0`

Candidate precision and recall are report-only in v0.3.2.1. They must not fail the release by themselves until the fixture corpus is large enough to support meaningful global thresholds.

## Failure Record Contract

Every failed hard-gate case must produce a stable failure record:

```json
{
  "case_id": "taghcase_scope_boundary",
  "layer": "document",
  "severity": "error",
  "reason_code": "wrong_auto_attach",
  "raw_candidate": "sqlite",
  "expected": {},
  "actual": {},
  "governance_reasons": ["scope_mismatch"]
}
```

Required reason codes for v1:

```text
wrong_auto_attach
manual_tag_mutation
trusted_filter_pollution
budget_violation
lifecycle_ineligible_auto_attach
unresolved_candidate_persisted
policy_mutation_by_harness
expected_candidate_missing
unexpected_candidate_created
expected_block_missing
expected_search_hit_missing
unexpected_search_hit
fixture_schema_invalid
unsanitized_fixture
doctor_hard_finding
```

Rules:

- Release gates and future consoler integration must not parse localized prose.
- The artifact must include minimal reproduction details: case id, raw candidate, expected, actual, and reason code.
- Aggregate metrics must not hide individual hard-gate case failures.

## Artifact Contract

The harness may emit diagnostic artifacts into a temporary or requested artifact directory:

```text
tag-harness-summary.json
tag-harness-failures.jsonl
tag-harness-report.md
```

Rules:

- Summary JSON is the CI contract.
- JSONL failures are the debugging contract.
- Markdown report is optional human output.
- Artifacts are not trusted user metadata.
- Artifacts must not be written into a production vault by default.

## Tag Search Checks

v0.3.2.1 validates only trusted tag-filter behavior.

In scope:

- `document_tags -> tags -> canonical resolution`
- exact trusted tag filter hits
- alias-to-canonical filter resolution
- merged tag resolution where existing v0.3.2 semantics allow it
- candidate/rejected/blocked/deprecated/archived state does not pollute trusted filters
- original source text can be found under expected trusted tag filter cases

Out of scope:

- search ranking
- hybrid search changes
- query expansion
- semantic retrieval
- retrieval packages
- `ask`

## Feedback Regression Loop

Add fixture support for feedback-derived regression cases.

Rules:

- Only reviewed Tag Feedback or Tag Governance Events can become harness cases.
- Export must be explicit.
- Repo fixtures must be sanitized before commit.
- Feedback-derived cases must not automatically train a model.
- Feedback-derived cases must not mutate production tag policy.
- Harness may produce Tag Policy Suggestions, but policy changes still require explicit review/accept workflows.

The implementation may add a small export helper only if needed for tests. A formal user CLI for export is deferred.

## Doctor Boundary

Harness and doctor have separate responsibilities:

- Harness proves expected behavior against fixtures and release gates.
- Doctor diagnoses real vault health.

v0.3.2.1 may add doctor checks only if needed to expose real tag integrity issues. Doctor must not run the full fixture suite and must not repair tags.

Potential doctor additions:

- unresolved governance candidate
- auto-attached lifecycle-ineligible tag
- trusted tag filter stale metadata
- tag governance event missing for accepted/rejected candidate
- repeated blocked candidate warning

## Acceptance Checklist

- Fixture schema is explicit and validated.
- Fixture corpus is synthetic or sanitized.
- Evaluation uses isolated eval vaults.
- Seed documents represent trusted current revision/chunk/FTS state.
- Harness calls existing tag governance/tagger/search services.
- Hard-gate fixtures use exact expectation matching.
- Summary JSON is stable and machine-readable.
- Failure records expose stable reason codes.
- Artifacts include minimal reproduction details.
- Dangerous hard-gate metrics are zero.
- Candidate precision/recall are report-only.
- Quantity control is explainable.
- Trusted tag search filters are relation-backed and unpolluted.
- Feedback-derived regression cases are explicit and sanitized.
- Harness does not mutate production tag policy or production vaults.
- No real providers, embeddings, network calls, or API keys are used.
- No production schema migration is added unless explicitly justified.
- Release gate passes locally.
- CI job is added after local pass.
- `docs/testing.md` and `docs/project-status.md` are updated after implementation.
