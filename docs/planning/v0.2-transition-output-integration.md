## Decision Summary

`transition` becomes the standard output renderer for indbase Markdown-derived outputs. It standardizes Markdown and derives requested export formats such as HTML, PDF, and DOCX. `indbase` keeps ownership of document identity, source bindings, immutable revisions, output records, vault paths, task visibility, errors, durable artifacts, hashes, and doctor checks.

This mirrors the swallow integration boundary:

```text
transition owns standardization and export rendering.
indbase owns trust.
export artifact != source revision.
source replacement creates a new immutable revision.
default search indexes source revisions only.
```

## Resolved Decisions

The following decisions are locked for v0.2 transition output implementation. If an older section in this document conflicts with this section, **Resolved Decisions** wins.

### Protected content (A+B) and span detection (v1)

- indbase sends a **span contract** to the bridge: `protected_spans` with offsets and kinds; transition must not modify protected byte ranges.
- indbase performs **post-hoc byte-for-byte** validation on every protected span in bridge output.
- Read-only export: `normalized.md` fails protected validation → `output_run.status = failed`.
- `doc normalize --replace-current`: bridge input is **body only** (**N-A1**); indbase writes fresh frontmatter for the new revision.
- **Citations v1 (D)**: no dedicated cite syntax detector; quoted source text is protected only when it falls under block quotes (B2) or future `<!-- indbase:literal -->` sentinels (B5, not emitted in v1).

**Span detection v1 (S-std)** applies to Markdown **body** bytes:

- **B1**: fenced code blocks (` ``` ` … ` ``` `, including info string).
- **B2**: block quotes (contiguous lines starting with `>`).
- **B3**: display math (`$$ … $$`; optional `\[ … \]` if enabled in the validator).
- **Not in v1**: inline backtick code (B4) — defer to v1.1.

**Export inputs (E-C1)**: treat the YAML frontmatter fence (`---` … `---` plus trailing newline) as one protected span over the **full file** before body rules run.

**Derived input extras**:

- **Translation (T-prot2)**: additionally protect each `### Source` section from its heading through the line before `### Translation`.
- **Accepted atomic note (N-prot2)**: additionally protect each `Citations:` block under a claim heading through the end of that claim section.

Protected-span rules live in indbase Python, **not** in `transition.config.json` (Cfg1).

### Translation export (v1)

- **CLI (T-cli1)**: `indb output export translation <translation_id>` only; load `translations.output_path` from DB.
- Require `translations.status = succeeded` and an on-disk file under `outputs/translations/`.
- **`output_sources` (T-bind1)**: one row per `source_chunk_id` in `source_chunk_ids_json`; `mapping_confidence = exact` (DB binding, not P1 text match).
- `input_kind = translation`, `input_id = translation_id`.

### Accepted atomic note export (v1)

- **CLI (N-cli1)**: `indb output export note <candidate_card_id>`; id is `candidate_card_id`, not a free path.
- Require `candidate_cards.status = accepted`, `accepted_note_path` under `notes/atomic/`, and matching note frontmatter.
- **`output_sources` (N-bind1)**: one row per `candidate_card_sources.source_chunk_id`; `mapping_confidence = exact`.
- `input_kind = accepted_atomic_note`, `input_id = candidate_card_id`.

### Transition config (Cfg1)

- **Whitelist only**: `runtime install` writes a safe default `transition.config.json`; unknown or forbidden keys fail validation.
- Allowed classes: render engine defaults, typography/fonts/CJK, trace verbosity; cache paths must stay under vault `.indbase/cache/transition`.
- Forbidden classes: source-binding or locator rewrite toggles, project config discovery/`extends`/search paths, in-place input writeback, paths outside the vault.
- Re-validate on every `output_run`; hand-edits that introduce forbidden keys fail with `transition_config_invalid` (config on disk is not auto-reverted).
- Record `config_hash` per run; config snapshots in evidence reflect the run that produced them.

### Chunk locator mapping

- **v1 (P1)**: after rechunking with `markdown_heading_v1`, copy `source_locator_json` only when old and new chunks share the same `heading_path` and **identical chunk `text` bytes** (`mapping_confidence = exact`).
- **v1.1 (P2)**: additionally allow locator inheritance when old chunk text lies entirely inside protected spans that survive A+B validation unchanged.
- Otherwise: record parent revision/chunk only (`mapping_confidence = parent_only`); do not copy page/time/web/archive locators.

### Node vs transition runtime

- **Node** is a host-environment responsibility. indbase detects Node and prints remediation; it does not install Node.
- **transition** is an indbase output-layer runtime responsibility: pinned package, bridge template, vault-local install layout, and explicit setup commands.
- **No implicit install**: `init`, `doctor`, and the first `output export` / `doc normalize` must **not** run `npm install` or equivalent.
- **Explicit install only**:

```text
indb output runtime install
indb output runtime status
```

- Per-vault runtime root: `.indbase/runtime/transition/` (`package.json` with pinned git SHA, `node_modules`, bridge script, transition config).
- `features.transition_output = true` is written only after `output runtime install` succeeds.

### Feature flag (F1)

- Default: `features.transition_output = false`.
- Only `indb output runtime install` may set `transition_output = true` in vault config.
- If an operator hand-edits `transition_output = true` without a complete runtime, output commands fail with `transition_runtime_missing` and doctor may report `transition_output_enabled_without_runtime`.
- When `transition_output = false`, all `output` and `doc normalize` commands fail with `transition_output_disabled`, even if a runtime directory exists.
- Ingest, search, and document inspection ignore this flag.

### Bridge JSON contract (C1) and invocation (B1+B3)

- indbase **owns and versions** bridge request/response schema (`contract_version: 1` in the indbase repo; golden fixtures for tests).
- The vault bridge script is a thin adapter over the pinned transition SDK.
- Each `output_run` uses **one** `node` subprocess; working directory is the vault runtime directory.
- Default transport: stdin/stdout JSON; large payloads use request/response files under `.indbase/cache/transition/jobs/<output_run_id>/`.
- Record `contract_version`, `transition_commit`, and `config_hash` on every `output_run`.
- `doctor --deep` may run a one-shot bridge smoke test; that is diagnosis only, not installation.

### Export scope and `--to` targets (E3, T1+T3)

- **v1 export inputs (all required)**: current or explicit source revision, translation output, accepted atomic note.
- **v1 normalize**: `doc normalize <doc_id> --replace-current` only; one active document at a time.
- `normalized.md` is **always** produced and validated; it is not selected via `--to`.
- `--to` accepts only `html`, `pdf`, and `docx`.
- If the operator passes no `--to`, treat the request as **md-only** (deliver `normalized.md`, do not run heavy render targets).
- `partial` / `succeeded` counts only **requested** html/pdf/docx targets; normalized failure always yields `failed`.

### Normalize failure and promotion (Nf2, Rvs1)

- Failed normalize runs keep `output_run` rows and durable evidence under `.indbase/artifacts/output_runs/...` when the bridge produced them.
- Never update `documents.current_revision_id` or `canonical_path` unless chunking and default FTS refresh for the new revision succeed (**Idx1**).
- When `features.embedding = true`, mark embeddings stale after successful promotion and tell the operator to run vector rebuild; embedding failure does **not** block promotion in v1.
- Protected validation runs **before** writing any new `sources/...__rev_N.md` file.
- If chunking or FTS fails after a revision row exists, keep the revision row and on-disk Markdown, set `promotion_status = never_promoted`, and leave the previous revision as current.
- On success: new revision `promotion_status = promoted` and becomes current; prior current revision becomes `superseded`.

### Archive and stale export (L1)

- Read-only export is allowed for archived documents and for explicit non-current `--revision` inputs.
- Record `input_archived` / `input_stale` (or equivalent) on the `output_run` and print a CLI warning.
- `doc normalize --replace-current` rejects archived documents and source shells.

### Concurrency (Lck2)

- Read-only exports may run concurrently, including multiple runs against the same source object.
- At most one incomplete `source_normalize_replace_current` run per `source_doc_id`; a second normalize fails with `normalize_already_running`.
- Export does not lock normalize and normalize does not lock export.

### Runtime reinstall (Up1)

- `output runtime install` may be repeated to upgrade the pinned commit.
- Never rewrite `transition_commit`, `contract_version`, or `config_hash` on existing `output_runs`.
- New runs use the newly installed pin; default doctor validates each run against its own recorded metadata.
- After reinstall, print an informational warning when older output runs exist under a previous commit.

### Bridge timeout (Tm1, Art1)

- Config key `bridge_timeout_seconds` (Cfg1 whitelist), default `300`.
- Subprocess timeout, non-zero exit, invalid JSON, or bridge crash → `output_run.status = failed` (never `partial` without a validated `normalized.md`).
- Do not publish partial artifacts under `outputs/exports/<output_run_id>/`; cache job files may remain for debugging until the run finishes.
- When the bridge still produced manifest/trace/report (or `response.json` with evidence paths), copy them into `.indbase/artifacts/output_runs/<output_run_id>/` and set `output_runs.evidence_*`; write `input_hashes.json` with `"partial": true` if normalized Markdown was not validated. Partial evidence does not imply export success.

## Goals

- Add `indb output export` for read-only output export.
- Add `indb doc normalize <doc_id> --replace-current` for user-approved source Markdown standardization.
- Persist immutable `output_runs` for export and normalization work.
- Persist `normalized.md` as the required transition output for export runs.
- Support requested HTML, PDF, and DOCX targets as derived artifacts.
- Allow users to replace the current source Markdown with transition-standardized Markdown through a new document revision.
- Keep old source revisions and old chunks intact.
- Keep output artifacts out of default source search.
- Diagnose missing or corrupted output artifacts through doctor.

## Non-goals

- Do not overwrite canonical Markdown files in place.
- Do not use a transition HTTP service.
- Do not parse transition CLI text as a stable API.
- Do not let transition own indbase document IDs, revision IDs, chunk IDs, frontmatter, tasks, errors, or doctor state.
- Do not index export artifacts in default search.
- Do not use project `transition.config.*` discovery implicitly.
- Do not replace swallow ingest conversion with transition.
- Do not implement ask, summaries, or model-backed synthesis as part of this work.

## Ownership Boundary

| Area | Owner | Rule |
| --- | --- | --- |
| Source document identity | indbase | `doc_id` remains stable and is never created by transition. |
| Source revision creation | indbase | A transition-normalized replacement writes a new immutable revision. |
| Markdown standardization | transition | transition may standardize Markdown body content through the local SDK bridge. |
| HTML/PDF/DOCX rendering | transition | transition renders requested targets from normalized Markdown. |
| Protected metadata | indbase | frontmatter and source bindings must be preserved or restored by indbase. |
| Output run records | indbase | indbase records input, hashes, status, targets, artifacts, and source bindings. |
| Durable evidence | indbase | transition cache is copied into `.indbase/artifacts/output_runs/...` before completion. |
| Search indexing | indbase | export artifacts are not indexed by default; replacement revisions are indexed as current source revisions. |
| Doctor | indbase | doctor validates indbase records, files, hashes, manifests, and bindings. |

## Runtime And Dependency Boundary

Use a local Node SDK bridge with a pinned transition dependency.

Initial pin:

```text
konglong-pro/transition.git#cf4a726bf9a5c3c9cb300fda38bcb54fac005f23
```

Runtime rules:

- Use a local SDK bridge invoked through a JSON request/response contract (C1, B1+B3).
- Do not call a transition HTTP service.
- Do not treat CLI text output as a stable API.
- Do not vendor transition into indbase.
- Install transition only through `indb output runtime install` under `.indbase/runtime/transition/`.
- Node is a host dependency; indbase does not install Node.
- Record transition package version, pinned commit, and `contract_version` when available.
- Missing Node, runtime files, or transition package must produce visible output failures, not silent fallback success.
- transition is required for the output layer but must not block existing ingest, search, or document inspection basics.

## Configuration

indbase owns the configuration used for transition output.

Suggested config shape:

```toml
[features]
transition_output = false

[output.transition]
runtime_dir = ".indbase/runtime/transition"
bridge_path = ".indbase/runtime/transition/transition-bridge.mjs"
config_path = ".indbase/runtime/transition/transition.config.json"
cache_dir = ".indbase/cache/transition"
bridge_timeout_seconds = 300
archive_required_artifacts = true
protect_source_bindings = true
```

Rules:

- Use only indbase-managed transition config under the vault runtime directory unless a future task explicitly adds another mode.
- Do not set `transition_output = true` except after `indb output runtime install` succeeds.
- Do not auto-discover `transition.config.*` from the current working directory, vault parent, or source project.
- Record the config hash in every output run.
- Any config that permits source-binding rewrites must be rejected.

## CLI Shape

Runtime setup (explicit install only):

```text
indb output runtime install
indb output runtime status
```

Read-only export:

```text
indb output export source <doc_id> [--revision <revision_id>] [--to html] [--to pdf] [--to docx]
indb output export translation <translation_id> [--to html] [--to pdf] [--to docx]
indb output export note <candidate_card_id> [--to html] [--to pdf] [--to docx]
indb output list
indb output show <output_run_id>
indb output open <output_run_id> [--format md|html|pdf|docx]
```

Source replacement:

```text
indb doc normalize <doc_id> --replace-current
```

Rules:

- `normalized.md` is always produced for export runs; omitting all `--to` flags means md-only delivery.
- `--to` selects optional html/pdf/docx targets only; there is no `--to md` flag.
- `output export` creates derived artifacts only.
- `doc normalize --replace-current` mutates document current state by creating a new immutable revision.
- `doc normalize --replace-current` v1 supports one document at a time.
- Any command that changes `current_revision_id` must be under `doc`, not hidden under `output export`.

## Read-only Export Pipeline

The authoritative pipeline stays in indbase:

```text
1. resolve export input
2. verify input object exists and is allowed
3. load Markdown content and source bindings
4. create output_run
5. call transition bridge with protected metadata and content
6. write normalized.md under outputs/exports/<output_run_id>/
7. write requested HTML/PDF/DOCX artifacts under the same output directory
8. copy transition manifest, trace, report, and config snapshot into .indbase/artifacts/output_runs/<output_run_id>/
9. record output_artifacts with paths, hashes, statuses, and errors
10. record output_sources for source doc/revision/chunk bindings
11. finish task and output_run
```

Status policy:

- If normalized Markdown fails, the run is `failed`.
- If normalized Markdown succeeds and all requested targets succeed, the run is `succeeded`.
- If normalized Markdown succeeds and one or more **requested** html/pdf/docx targets fail, the run is `partial`.
- Successful artifacts remain usable for `partial` runs.
- Non-requested render targets do not affect `partial` vs `succeeded`.

## Normalize And Replace Current Pipeline

`doc normalize --replace-current` is not an export-only workflow. It creates a new source revision.

Pipeline:

```text
1. load active current document and current revision
2. reject source shells, archived documents, missing current revisions, and unreadable Markdown
3. create output_run with mode = source_normalize_replace_current
4. call transition bridge against current source Markdown
5. validate protected metadata and protected literal blocks (A+B); abort before any new source file if validation fails
6. copy transition evidence into .indbase/artifacts/output_runs/<output_run_id>/
7. write a new sources/...__rev_000N.md file using indbase frontmatter
8. insert document_revisions row for the new revision with derivation and promotion_status
9. mark old current chunks as non-current without deleting them
10. chunk the new revision
11. rebuild or update FTS/vector current indexes
12. only after steps 7-11 succeed: set new revision promotion_status = promoted, prior current = superseded, update documents.current_revision_id and canonical_path
13. record source derivation from parent revision and output_run
14. finish task and output_run
```

Rules:

- Failed runs may keep output_run evidence; they must not change current_revision_id.
- If step 10 or 11 fails after step 8, keep the new revision row and file with promotion_status = never_promoted.
- The old revision remains immutable and must not be deleted.
- The old canonical Markdown file must not be overwritten.
- The new revision should be marked as derived by transition.
- The transition output may be trusted as source body content only because the user explicitly ran the replacement command.
- Source locators are inherited only when mapping from old chunks to new chunks is provable.
- When locator mapping is not provable, keep parent revision/chunk provenance instead of copying page, time, web, or archive locators blindly.

## Protected Content Rules

indbase must protect and validate:

- indbase frontmatter
- `doc_id`
- `revision_id`
- source document, revision, and chunk IDs
- citations
- quote blocks and source excerpts
- code blocks
- math blocks
- other literal blocks marked as protected by indbase

For all bridge calls:

- send `protected_spans` in the indbase-owned contract (C1)
- validate protected bytes after the bridge returns (A+B)

For read-only exports:

- protected content must remain byte-for-byte equivalent in `normalized.md`
- a protected-content mismatch fails the run

For source replacement:

- indbase writes fresh frontmatter for the new revision
- protected source excerpts, citations, code, and math must remain byte-for-byte equivalent
- if protected body content changes, the replacement fails before creating a revision

## Artifact Policy

User-visible artifacts:

```text
outputs/
  exports/
    <output_run_id>/
      normalized.md
      output.html
      output.pdf
      output.docx
```

Durable evidence:

```text
.indbase/
  artifacts/
    output_runs/
      <output_run_id>/
        transition_manifest.json
        transition_trace.jsonl
        transition_report.json
        config.json
        input_hashes.json
```

Rules:

- transition cache is not durable evidence.
- Evidence files must be copied into `.indbase/artifacts/output_runs/...`.
- Artifact paths stored in DB must be vault-relative.
- Paths must not point to temp directories, absolute paths, parent-directory escapes, or transition cache as durable evidence.
- `doc normalize --replace-current` writes the resulting Markdown into `sources/`, not `outputs/exports/`.

Recommended revision derivation additions:

```text
document_revisions
  parent_revision_id TEXT
  derived_from_output_run_id TEXT
  derivation_kind TEXT
  derivation_tool TEXT
  promotion_status TEXT NOT NULL   -- promoted | superseded | never_promoted
```

`promotion_status` values:

- `promoted`: revision is or was the document current revision
- `superseded`: revision was current and was replaced by a newer promoted revision
- `never_promoted`: revision was created by normalize but never became current (for example chunk/FTS failure)

`quality_signals_json` and report JSON may hold detailed formatting diagnostics, but primary relationships needed by doctor should be queryable directly.

## Doctor Checks

Default doctor should validate existing output state:

- output runs reference existing tasks when present
- output runs reference existing source documents and revisions when present
- created revisions reference valid output runs
- output artifacts have vault-relative safe paths
- required `normalized.md` artifact exists for export runs
- artifact hashes match files on disk
- evidence manifest and trace paths exist when required
- export artifacts are not indexed in default source search
- transition-normalized current revisions have chunks and index rows
- old revisions remain present after replacement
- output sources do not reference missing chunks unless the mapping is explicitly parent-only
- `never_promoted` revisions are not current and must not have default-search current chunks
- failed normalize runs with evidence do not imply a current revision change

Default doctor should not make every vault unhealthy just because PDF/DOCX tools are missing.
Default doctor must not install Node packages or modify `transition_output`.

`doctor --deep` may run heavier checks:

- Node executable availability
- transition package import smoke
- bridge JSON contract smoke
- HTML render smoke
- pandoc smoke
- PDF engine smoke
- CJK font smoke
- DOCX export smoke

Doctor diagnoses only. It must not silently repair output runs or regenerate artifacts.

Required coverage:

- fake bridge contract success
- fake bridge failure
- missing transition dependency
- source revision read-only export
- translation output export
- accepted atomic note export
- partial target export failure
- artifact hash mismatch doctor finding

- export artifacts excluded from default search
- source normalize replacement creates a new revision
- old revision remains present after replacement
- new replacement revision becomes current and searchable
- protected frontmatter and body blocks cannot be altered
- locator inheritance only when mapping is provable
- stale or archived exact export is allowed and labeled
- archived document replacement is rejected
- source shell replacement is rejected
- normalize chunk/FTS failure leaves `never_promoted` revision and unchanged current
- `transition_output` cannot be used without explicit runtime install
- translation export requires `translation_id` and exact chunk bindings
- atomic note export requires accepted `candidate_card_id` and citation protection
- config whitelist rejects forbidden transition keys
- bridge timeout marks run failed without export artifacts
- concurrent normalize on the same doc is rejected

Assertions:

- no canonical Markdown file is overwritten in place
- output run status is correct
- artifact files are vault-relative
- evidence is copied out of transition cache
- task and error state is visible
- doctor detects broken output state
