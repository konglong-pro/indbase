## Decision Summary

v0.3.3 adds deterministic retrieval evaluation and answer-readiness checks on top of v0.3.2 `indb retrieve`.

This phase does not implement `indb ask`. It prepares the contract that a future ask implementation will consume:

```text
retrieve -> persisted retrieval_run_id -> readiness report -> future ask
```

Core invariants:

```text
Evaluation measures retrieval quality.
Readiness decides whether a retrieval_run is safe enough for future ask.
Ask is still not implemented.
No model judge is used in v0.3.3.
Evaluation must be repeatable in CI.
```

## Confirmed Implementation Clarifications

These decisions were accepted before implementation planning and are part of the v0.3.3 contract.

### Main Goal

Build evaluation assets and an answer-readiness contract.

Do not treat v0.3.3 as a broad retrieval hardening phase. Existing v0.3.2 retrieval behavior is the baseline.

### Storage Model

Store evaluation and readiness records in the vault database, and support JSONL import/export for versioned fixtures.

This gives v0.3.3 both:

- durable vault-local audit state
- repo-owned, reviewable evaluation cases for CI and regression gates

### CLI Surface

Use a dedicated `eval` namespace:

```text
indb eval retrieval import <jsonl>
indb eval retrieval export --suite <name>
indb eval retrieval run --suite <name>
indb eval retrieval list
indb eval retrieval show <eval_run_id>
indb eval retrieval readiness <retrieval_run_id>
```

This keeps future answer/card evaluation extensible without overloading `indb retrieval`.

### Answer Readiness

Answer readiness is a first-class persisted report for a `retrieval_run_id`.

Verdicts:

```text
ready
needs_more_evidence
not_ready
```

Rules:

- `ready` means the package passes deterministic ask-input checks.
- `needs_more_evidence` means a future answer may be possible but should require more retrieval or user review.
- `not_ready` means future ask must refuse or ask the user to retrieve again.

Future `indb ask` v1 should accept a `retrieval_run_id` with a `ready` readiness report. It should not run hidden retrieval internally.

### Readiness Strictness

Use conservative graded readiness.

Hard failures become `not_ready`. Caution conditions become `needs_more_evidence`, not automatic failure.

Examples:

- failed retrieval run -> `not_ready`
- zero retrieval items -> `not_ready`
- quote mismatch -> `not_ready`
- missing source binding -> `not_ready`
- too few results -> `needs_more_evidence`
- duplicate-heavy package -> `needs_more_evidence`
- all or most items have `profile_missing` -> `needs_more_evidence`
- warnings present but evidence is otherwise strong -> `ready` or `needs_more_evidence` depending on policy thresholds

### Evaluation Case Granularity

Evaluation cases are evidence-level, not only document-level.

Cases may express:

- expected document ids
- expected quote substrings
- forbidden document ids
- minimum result count
- minimum unique document count
- expected readiness verdict
- expected warning or blocker codes

Do not limit v0.3.3 to "query returns any result" checks. That is too weak for answer readiness.

### Benchmark Source

Use both:

- small repo-owned JSONL fixtures for deterministic hard gates
- real-corpus dogfood exports as candidate cases for later review

Real-corpus dogfood remains optional and must not become a required PR blocker in v0.3.3.

### Retrieval Hardening Scope

Only make retrieval changes that are necessary to expose evaluation or readiness risk.

Allowed:

- clearer warnings
- readiness metrics derived from existing retrieval rows
- CLI hints that evaluation can consume

Not in scope:

- rewriting retrieval ranking
- changing hard filter semantics
- changing quote extraction algorithm
- adding MMR or chunk similarity dedupe
- adding model-based reranking

### Judge Source

Use deterministic checks only.

Do not use:

- real LLM judge
- remote evaluation provider
- hidden network calls
- fake-provider dependency for main v0.3.3 behavior

The future may add optional semantic judges, but hard v0.3.3 gates must remain deterministic.

### Gate Level

Add a C4 hard gate:

```text
scripts/v033_retrieval_eval_release_gate.py
```

This gate should run in CI after C3.

Layer E real-corpus evaluation or dogfood remains optional.

### Observability

Use eval/readiness table status and `error_json` fields for failure visibility.

Do not create task records for v0.3.3 eval runs. The workflows are synchronous and lightweight, similar to v0.3.2 retrieval runs.

## Goals

- Make retrieval quality measurable through deterministic cases.
- Persist evaluation cases, runs, and results.
- Support JSONL import/export so evaluation fixtures can live in version control.
- Add answer-readiness reports for persisted retrieval runs.
- Create a hard C4 gate for regression prevention.
- Convert v0.3.2 dogfood findings into explicit evaluation dimensions.
- Preserve v0.3.2 retrieval behavior unless a small reporting change is required.

## Non-goals

- Do not implement `indb ask`.
- Do not generate answers, summaries, claims, cards, or notes.
- Do not write `citations`.
- Do not call LLMs or model judges.
- Do not add real providers, auth, network calls, or cost-bearing services.
- Do not rewrite retrieval ranking, filters, quote extraction, vector search, or taxonomy boosts.
- Do not make real-corpus dogfood a hard CI gate.
- Do not add TUI flows in v0.3.3 unless explicitly requested later.
- Do not use evaluation to mutate taxonomy, profiles, source documents, revisions, chunks, or retrieval rows.

## Eval Case JSONL Contract

Each JSONL row represents one evaluation case.

Required fields:

```json
{
  "suite": "v033_core",
  "name": "tag filter returns tagged RAG doc",
  "query": "retrieval tag:rag",
  "expect": {}
}
```

Optional fields:

```json
{
  "case_id": "retrcase_static_tag_filter_rag",
  "options": {
    "mode": "hybrid",
    "top_k": 8,
    "candidate_k": 40,
    "per_doc_limit": 3
  },
  "expect": {
    "expected_doc_ids": ["doc_..."],
    "expected_quote_contains": ["retrieval augmented generation"],
    "forbidden_doc_ids": ["doc_..."],
    "min_result_count": 1,
    "min_unique_docs": 1,
    "expected_readiness": "ready",
    "expected_warnings": [],
    "forbidden_warnings": ["filter_false_negative"]
  },
  "notes": "Why this case exists."
}
```

Rules:

- Invalid JSONL rows fail import visibly.
- Missing required fields fail import.
- Unsupported expectation keys fail import unless explicitly allowed.
- Export must be deterministic and stable enough for code review.

## Readiness Policy

Policy version:

```text
answer-readiness-v1
```

Inputs:

- one `retrieval_run`
- its `retrieval_items`
- source chunk text for quote validation
- run warnings and item reasons

Metrics:

- item count
- unique doc count
- quote validity count
- minimum quote length
- duplicate doc ratio
- profile-missing item ratio
- warning count
- failed/partial/succeeded run status

Default verdict rules:

```text
not_ready:
  retrieval_run missing
  retrieval_run.status = failed
  item_count = 0
  any item missing doc/revision/chunk
  any item quote empty
  any item quote not exact substring of chunk text

needs_more_evidence:
  item_count < configured minimum
  unique_doc_count < configured minimum for broad queries
  duplicate_doc_ratio too high
  profile_missing ratio too high
  warnings exceed caution threshold
  retrieval_run.status = partial

ready:
  no blockers
  caution thresholds acceptable
```

Default thresholds:

```text
min_items = 2
min_unique_docs = 1
max_duplicate_doc_ratio = 0.75
max_profile_missing_ratio = 0.80
max_warning_count = 10
min_quote_chars = 20
```

Hard quote/source binding failures remain `not_ready` even if an eval case overrides thresholds.

## Evaluation Flow

### Import Cases

```text
indb eval retrieval import cases.jsonl
  -> parse JSONL
  -> validate required fields
  -> validate options and expectations
  -> upsert retrieval_eval_cases
  -> report imported/updated/rejected counts
```

### Run Suite

```text
indb eval retrieval run --suite v033_core
  -> load active cases
  -> create eval run
  -> for each case:
       run retrieve using case query/options
       create readiness report for retrieval_run_id
       compare results to expectations
       write eval result
  -> finish eval run
  -> exit nonzero when any result failed or errored
```

### Readiness Report

```text
indb eval retrieval readiness <retrieval_run_id>
  -> load retrieval run and items
  -> compute deterministic metrics
  -> persist readiness report
  -> render verdict, blockers, warnings, metrics
```

### Export Cases

```text
indb eval retrieval export --suite v033_core
  -> load active cases
  -> write deterministic JSONL to stdout or --output path
```

## Acceptance Checklist

- Eval cases can be imported and exported as deterministic JSONL.
- Eval runs execute cases and persist result records.
- Eval results link to retrieval runs and readiness reports.
- Evidence-level expectations can pass and fail deterministically.
- Readiness reports classify ready, needs-more-evidence, and not-ready packages.
- Future ask has a clear input contract: a readiness-checked `retrieval_run_id`.
- No model judge, network call, or real provider is used.
- Retrieval ranking, filter semantics, and quote extraction are not redesigned.
- Doctor covers corrupt eval/readiness records.
- C4 release gate passes.
