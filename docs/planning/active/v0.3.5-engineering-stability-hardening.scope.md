# v0.3.5 Engineering Stability Hardening Scope

Status: completed. The user explicitly authorized implementation of the full
v0.3.5 scope on 2026-06-09. Stage 1 and Stage 2 are retained here as the
completed scope and closeout reference for the v0.3.5 baseline.

Date: 2026-06-09

## Goal

Reduce the engineering stability debt exposed after the v0.3.4 Provider
Evidence / Trust Correlation baseline.

This scope keeps the v0.3.4 trust rule:

```text
provider output = evidence or candidate
indbase decision = trusted state
```

The work is split into two stages.

## Stage 1: Provider Reliability / Packaging Gate

### Goal

Make provider-backed workflows provable in installed environments, not only in
source-tree fake-provider tests.

Execution detail:
`docs/planning/active/v0.3.5-stage1-provider-reliability-packaging.execution.md`

Agent rules:
`docs/agents/current/v0.3.5-stage1-provider-reliability-packaging/AGENTS.md`

### Scope

- Fix packaging gaps so installed wheels include provider integration modules.
- Keep `indbase_integrations` as the provider adapter package and include it in
  built wheels. Do not move provider adapter implementation into
  `indbase_core`.
- Put `consoler_agent_sdk` on the correct optional dependency path and prove
  the installed indbase wheel with the installed consoler SDK, without
  hard-coding local consoler repository paths.
- Prefer a versioned install coordinate for `consoler_agent_sdk`, such as a
  package index release with an explicit version range. A pinned Git direct
  reference is acceptable only as a temporary bridge and must be marked for
  replacement by a versioned package.
- Use the stable consoler SDK package coordinate
  `consoler-agent-sdk==0.1.0` for the strong installed-wheel consoler contract.
  The package declares protocol compatibility independently through
  `SUPPORTED_PROTOCOL_VERSION = "0"` in the consoler SDK runtime.
- Pin the indbase `consoler-agent` extra exactly to
  `consoler-agent-sdk==0.1.0` for Stage 1 reproducibility. Broader version or
  protocol ranges are future policy work.
- Install `consoler-agent-sdk` only through the `consoler-agent` extra.
  Ordinary development sync and general pytest must not require internal
  package index access; the dedicated installed-wheel consoler contract job
  installs the extra and blocks when required.
- CI must treat the consoler SDK package index as a trusted dependency source.
  Internal or mainline PR contexts with package-index access block on the
  installed-wheel consoler contract. Fork-style contexts without package-index
  credentials may explicitly skip that job, but main, internal PR, and release
  contexts must not skip it.
- The consoler SDK install path is documented externally as
  `pip install consoler-agent-sdk==0.1.0` from the internal package index.
  The consoler-side package checks reported before Stage 1 planning were:
  `corepack pnpm test:python-sdk`, `corepack pnpm test:python-sdk-package`,
  and dry-run `corepack pnpm publish:python-sdk` passed; guarded publish
  failed as expected without `CONSOLER_PYPI_REPOSITORY_URL`.
- Keep swallow optional dependency installation explicit and visible through
  doctor output.
- Ordinary PR CI validates the swallow extra metadata and doctor output for a
  missing optional install. Scheduled, manual, or release jobs install
  `--extra swallow` and run real swallow smoke.
- Add transition bridge distribution smoke coverage for packaged installs.
- Installed smoke gates must build an indbase wheel, install it into a fresh
  temporary virtual environment, and run checks from outside the source tree so
  source-tree imports cannot hide packaging gaps.
- Transition bridge distribution smoke must run a minimal Node bridge
  normalization from the installed wheel and prove evidence copy. Pandoc, PDF,
  and document-engine coverage remains optional or formal-release smoke, not
  ordinary PR CI.
- Introduce a provider health surface that reports configured state, runtime
  availability, provider version, binding profile, capability compatibility,
  and smoke status.
- Update `docs/contracts/provider-capability-contract.md` with the durable
  provider health, failure class, and evidence completeness shapes introduced
  by Stage 1.
- Add canonical provider failure classes for unavailable providers, timeouts,
  contract violations, low-quality candidates, artifact copy failures, partial
  success, unsupported inputs, and unknown provider failures. Store the
  canonical class on provider run records while preserving existing provider
  and indbase error code fields.
- New failed or partial provider runs must record a failure class. Upgraded
  historical rows may keep a null class, but doctor should report a warning for
  failed or partial provider runs that cannot be classified.
- `provider_partial_success` is a non-fatal failure class for
  `provider_status = partial`. Whether partial output creates review work is a
  capability policy decision: partial export may remain a visible partial
  result, while partial ingest or low-quality candidates usually enter review.
- Add evidence completeness checks for copied evidence roots, manifest refs,
  trace refs, evidence index readability, and vault-relative artifact refs.
- Define required evidence roles by capability policy rather than one global
  artifact list. Every provider run must still leave an indbase-owned evidence
  index or bounded failure manifest so failures are not visible only in
  provider logs.
- Treat `provider_artifact_copy_failed` as an indbase evidence adoption
  failure. The provider may have returned success or partial, but
  `evidence_status = copy_failed` means indbase did not durably adopt required
  artifacts and must not treat the operation as trusted complete.
- Upgrade provider doctor output from import checks toward actionable runtime,
  capability, evidence, and smoke status.
- Split provider health into cheap and smoke levels. Ordinary doctor defaults
  to cheap checks; release smoke gates run sample-level checks. A future
  `indb doctor --provider-smoke` surface is optional, not required for the
  first Stage 1 implementation.
- Keep ordinary doctor provider health output stable and omit `checked_at`.
  Provider run timestamps and smoke script logs remain the timing evidence.
- Provider health warnings and errors should be structured findings with stable
  codes, severity, message, optional failure class, and required/skipped
  context. Transitional string warnings may be normalized into structured
  findings.

### Acceptance Signals

- Fake provider gate remains deterministic and proves provider contract,
  provider run, failure mapping, evidence copy, and artifact view behavior.
- PR CI blocks on fake provider gate, installed wheel import smoke, and
  transition bridge distribution smoke.
- PR CI blocks on an installed-wheel consoler agent contract smoke that uses a
  real installable `consoler-agent-sdk==0.1.0` dependency instead of local
  consoler repository paths.
- Formal release blocks on required real provider smoke when
  `INDBASE_PROVIDER_SMOKE_REQUIRED=1` is set.
- Swallow real smoke remains outside ordinary PR CI by default, but has an
  explicit install path, doctor output, and release-required mode.
- Real provider smoke proves the minimum swallow and transition runtime path
  when explicitly required by environment.
- Doctor reports provider health in a way that distinguishes missing optional
  installs, unavailable runtimes, contract mismatches, artifact copy failures,
  and skipped real smoke.
- Provider failures enter visible task, error, review, doctor, or command
  output surfaces according to failure class.
- Provider artifact views continue exposing `indbase://...` references instead
  of provider cache paths.
- Stage 1 hardens provider evidence artifact views against provider cache
  paths, provider URIs, raw trace bodies, private cache paths, and temporary
  directory leaks. It does not globally remove existing `vault_path` metadata
  from unrelated consoler artifact views.

### Non-Goals

- No dynamic plugin marketplace.
- No ordinary user-facing provider selection flags.
- No default HTTP, queue, or MCP provider profiles.
- No automatic retry or fallback execution in this stage; policy metadata may
  be recorded for future work.
- Failure classification may record lightweight policy metadata such as
  `retryable`, `fallback_candidate`, and `recommended_action` in provider run
  metadata or doctor output, but Stage 1 must not add a retry scheduler or
  fallback execution workflow.
- No provider ownership of trusted source revisions, chunks, search indexes, or
  output records.

### Stage 1 Implementation Slices

#### Slice 1: Packaging / Installed Wheel Smoke

Implementation tasks:

- Include `indbase_integrations` in built wheels.
- Pin the `consoler-agent` extra to `consoler-agent-sdk==0.1.0`.
- Add an installed wheel smoke script that builds an indbase wheel, installs it
  into a fresh temporary virtual environment, and runs checks from outside the
  source tree.
- Add PR CI coverage for installed wheel imports and the installed-wheel
  consoler agent contract smoke in trusted package-index contexts.

Tests and gates:

- Wheel import smoke proves `indbase_core`, `indbase_cli`, `indbase_agent`, and
  `indbase_integrations` import from the installed wheel.
- Consoler contract smoke installs `consoler-agent-sdk==0.1.0` through the
  `consoler-agent` extra and proves artifact block / artifact view contract
  behavior without local consoler repository paths.
- CI skips the consoler contract only in fork-style contexts without package
  index credentials; main, internal PR, and release contexts must block on it.

#### Slice 2: Provider Failure Classification

Implementation tasks:

- Add `provider_runs.failure_class` through a migration.
- Add a canonical provider failure class model and mapping layer.
- Define `provider_unavailable` as provider invocation being impossible because
  required runtime, package, binary, binding, or config is missing or disabled.
- Define `provider_contract_violation` as a reachable provider or provider
  response violating required contract, version, schema, capability, or
  evidence shape.
- Define `provider_low_quality_candidate` as a readable candidate that fails
  indbase adoption or promotion quality policy. It is primarily for ingest
  candidates; normalize may use it for quality failure, while schema or
  protected-span violations remain contract violations. Export target failures
  must not use this class.
- Define `provider_artifact_copy_failed` as indbase failing to copy or adopt
  otherwise returned provider artifacts into vault-owned evidence.
- Write failure class values for new failed and partial provider runs while
  preserving existing provider and indbase error code fields.
- Record lightweight policy metadata such as `retryable`,
  `fallback_candidate`, and `recommended_action` without executing retries or
  fallback.

Tests and gates:

- Contract tests cover every canonical failure class.
- Provider run tests prove new failed and partial rows record `failure_class`.
- Doctor reports a warning for failed or partial provider runs that lack a
  failure class after upgrade.
- Existing provider error code tests remain compatible.

#### Slice 3: Evidence Completeness / Provider Artifact Boundary

Implementation tasks:

- Define capability-level required evidence roles for ingest, normalize, export,
  and pre-invocation failure cases.
- Add evidence completeness checks for evidence root, evidence index,
  required refs, artifact copy status, and vault-relative copied artifact refs.
- Classify artifact copy/adoption failures as
  `provider_artifact_copy_failed` without blaming provider backend execution.
- Harden provider evidence artifact views against provider cache paths,
  provider URIs, raw trace bodies, private cache paths, and temporary
  directory leaks.

Tests and gates:

- Evidence store tests cover success, missing required evidence, invalid
  evidence index, and copy failure.
- Provider doctor tests report incomplete copied evidence.
- Artifact view tests prove provider evidence views expose only bounded
  summaries and `indbase://...` references.

#### Slice 4: ProviderHealth / Doctor / Real Smoke

Implementation tasks:

- Add a provider health shape to the provider capability contract.
- Implement cheap provider health checks for configured state, package/version,
  binding profile, capability compatibility, and runtime availability.
- Add a binding drift check between the reviewable repository
  `capability-bindings.yaml` default and the Python static registry. Stage 1
  does not make YAML the runtime source.
- Keep ordinary doctor on cheap checks by default.
- Add smoke-level checks for release gates, including transition bridge minimal
  normalize from the installed wheel and real provider smoke when required.
- Keep swallow real smoke out of ordinary PR CI by default while documenting
  install and release-required paths.

Tests and gates:

- Doctor tests cover missing optional swallow install, missing Node runtime,
  capability mismatch, skipped smoke, and smoke-required failure.
- Transition distribution smoke runs minimal Node bridge normalization and
  proves evidence copy from the installed wheel.
- `provider_fake_release_gate.py` remains deterministic.
- `provider_real_smoke.py` remains environment-gated and fails when required
  runtime is missing under `INDBASE_PROVIDER_SMOKE_REQUIRED=1`.

### Stage 1 Proposed Gate Scripts

- `scripts/provider_installed_wheel_smoke.py`: build an indbase wheel, install
  it into a temporary virtual environment, run from outside the source tree,
  and prove installed package imports and package data.
- `scripts/provider_transition_distribution_smoke.py`: run minimal transition
  Node bridge normalization from the installed wheel and prove provider evidence
  copy.
- `scripts/provider_consoler_contract_smoke.py`: install indbase with
  `--extra consoler-agent`, use `consoler-agent-sdk==0.1.0`, and prove the
  installed-wheel consoler agent artifact contract without local consoler repo
  paths.
- `scripts/provider_stage1_release_gate.py`: aggregate the fake provider gate,
  installed wheel smoke, transition distribution smoke, and consoler contract
  smoke when the consoler package index is available or required.
- `INDBASE_CONSOLER_CONTRACT_REQUIRED=1` upgrades missing
  `consoler-agent-sdk==0.1.0` or consoler contract smoke failure from explicit
  skip to hard failure. Trusted CI contexts must set it; fork-style contexts may
  leave it unset and must print an explicit skip reason.
- Existing `scripts/provider_fake_release_gate.py` remains the deterministic
  fake provider gate.
- Existing `scripts/provider_real_smoke.py` remains the environment-gated real
  provider smoke.

## Stage 2: Normalize Replace / Index Lineage Gate

### Goal

Make current revision replacement and source search indexing provable across
revision, chunk, FTS, search, provider evidence, and doctor surfaces.

Execution detail:
`docs/planning/active/v0.3.5-stage2-normalize-index-lineage.execution.md`

Agent rules:
`docs/agents/current/v0.3.5-stage2-normalize-index-lineage/AGENTS.md`

### Scope

- Add a dedicated normalize replace regression suite for the full chain:
  previous revision, new revision, chunks, FTS, source search, output run,
  provider run, copied evidence, locator mappings, review items, and errors.
- Normalize replace regression should assert the provider/output evidence
  invariants required by this workflow, including adopted provider run,
  copied evidence status, capability-required evidence, output artifact trust,
  and absence of provider evidence in default source search. It does not need
  to repeat the full Stage 1 failure taxonomy matrix.
- Normalize replace regression must also prove FTS metadata preservation for
  title, category, and trusted formal tags on the new current FTS rows.
- Add focused archive/restore interaction tests so lineage doctor does not
  mistake archived historical FTS/lineage rows for current drift, while source
  search continues excluding archived documents.
- Add small agent-visible artifact leakage regression tests for normalize,
  output, and provider evidence views. Blocks must not expose local absolute
  vault paths, provider cache paths, `file://`, provider URIs, or raw trace
  bodies beyond bounded summaries. Do not change consoler protocol from this
  repository.
- `vault_path` may remain internal artifact retrieval metadata, but returned
  agent-visible blocks and JSON content must not expose absolute local vault
  paths. Use bounded identifiers, relative artifact refs, or `indbase://...`
  URIs instead.
- Removing agent-visible `vault_path` from returned artifact view shapes is an
  allowed v0.3.5 contract change. It requires regression tests and a consoler
  coordination note. Internal retrieval metadata input remains unchanged.
- Add failure-path tests proving provider, transition, chunking, and indexing
  failures do not move `current_revision_id` to half-promoted revisions.
- Normalize replace has strong trusted-state atomicity requirements. Failures
  must leave the document current pointer, current chunks, FTS rows, and source
  search usable for the previous revision. Any new revision written before
  failure must not become current and must be marked `never_promoted` or remain
  traceable through output/provider failure evidence.
- Successful normalize replace keeps previous revisions and chunks durable.
  Previous chunks must become `is_current = 0`; current source search must
  exclude old revision chunks and old FTS rows.
- Stage 2 may extract internal normalize replace workflow helpers to improve
  locality around revision promotion, chunking, FTS lineage, and failure
  handling. Public output service APIs must remain unchanged. Regression tests
  should be written before restructuring.
- Add index lineage or companion build records so indexed chunks can be traced
  to `doc_id`, `revision_id`, `chunk_id`, and `index_build_id`.
- Stage 2 may add schema migrations for companion index lineage tables, such
  as `index_builds` and `index_build_entries`. These records prove FTS build
  coverage but do not replace `chunks_fts` or change source search ranking.
- Expected migration name is `0014_source_fts_lineage.sql`. Expected lineage
  tables are `index_builds` and `index_build_entries`. Stage 2 uses
  `index_kind = source_fts`; build status values are `running`, `succeeded`,
  and `failed`; entry status values are `indexed`, `skipped`, and `failed`.
- Stage 2 must implement lineage for `source_fts`. The schema may reserve
  `index_kind` for future embedding/vector lineage, but embedding writers are
  not required to adopt lineage in this stage.
- Keep `chunks_fts` schema unchanged. Store `index_build_id` and per-chunk
  lineage only in companion tables, and let doctor join companion lineage to
  FTS rows when proving coverage.
- Each indexer call should create its own `source_fts` build. Full rebuilds
  create vault-level builds; `reindex_document_fts` creates doc-level builds.
  Build metadata should record the trigger, such as `normalize_replace`,
  `manual_rebuild`, or metadata refresh.
- Lineage represents FTS row materialization, not only chunk text extraction.
  Metadata-only FTS refreshes should also create lineage builds with a
  `metadata_refresh` trigger.
- Upgraded historical FTS rows may initially lack lineage and should surface as
  doctor warnings. Stage 2 writes complete lineage for new rebuild,
  reindex-document, and normalize-replace indexing paths.
- Do not backfill a synthetic verified index build during migration. Missing
  lineage on upgraded historical FTS rows should remain visible until an FTS
  rebuild creates real lineage.
- Extend doctor drift detection so current chunks, FTS rows, current revision
  pointers, and index lineage agree.
- Doctor should report trusted current/search breakage as errors, including
  current chunks missing from FTS, FTS rows pointing to missing records or
  non-current revisions, current documents without current chunks, and complete
  index builds whose entries do not match current chunks. Upgraded historical
  FTS rows without lineage and non-current old lineage should be warnings.
  Empty vault and last successful build summaries may be info.
- Add retrieval regression thresholds for fixed corpora and query sets so
  chunking or ranking changes cannot silently degrade key source queries.
- Store retrieval regression fixtures under `tests/fixtures/` and run them
  through the existing retrieval evaluation machinery in an isolated temporary
  vault. Do not depend on external corpora for the PR gate.
- Regression expectations should primarily bind to current document/revision
  and required quote or text needle. Exact `chunk_id` expectations are optional
  so ordinary chunk boundary improvements do not freeze the chunker.
- A small deterministic retrieval regression gate is a PR CI blocker. Larger
  dogfood or real corpus retrieval evaluation remains scheduled, manual, or
  formal-release coverage.

### Acceptance Signals

- Normalize replace creates a new immutable revision, promotes it, demotes old
  chunks from current status, indexes only new current chunks, and leaves old
  source revisions intact.
- Source search never returns stale revision chunks after normalize replace.
- Doctor detects missing current FTS rows, stale FTS rows, incomplete index
  builds, and lineage drift.
- Retrieval evaluation fails when critical queries lose required hits or drop
  below approved thresholds.
- Output and provider evidence remain derived/evidence artifacts and do not
  enter default source search.
- Stage 2 implementation must update
  `docs/contracts/source-search-contract.md` with durable source FTS lineage
  and drift doctor rules.
- Stage 2 implementation must update `docs/contracts/artifact-contract.md`
  and, if needed, `docs/contracts/consoler-agent-boundary.md` with durable
  agent-visible artifact view leakage rules.

### Execution Order

1. Add failing normalize replace regression tests.
2. Add failing source FTS lineage, indexer, and doctor drift tests.
3. Add failing agent-visible artifact leakage tests.
4. Add failing retrieval regression threshold tests.
5. Implement migration and lineage writer integration.
6. Implement minimal normalize replace internal workflow helpers and fixes.
7. Implement artifact view redaction and contract documentation updates.
8. Implement retrieval regression gate.
9. Wire the focused v0.3.5 gate into CI and update testing/status docs.

### Non-Goals

- No retrieval ranking rewrite as part of this hardening scope.
- No `indb ask`, generated answers, summaries, claims, cards, or LLM judges.
- No physical deletion of old revisions or chunks in normal workflows.
- No consoler protocol, runtime, store, or schema changes from this repository.

- Keep real provider smoke environment-gated unless release policy changes.
- Stage 2 closeout must include CI gate evidence plus one dogfood smoke record

  completed.
