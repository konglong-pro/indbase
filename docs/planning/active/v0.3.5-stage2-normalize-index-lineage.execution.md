# v0.3.5 Stage 2 Normalize Replace / Index Lineage Gate Execution Plan

Status: completed. This execution plan is retained as the Stage 2 closeout
reference for the completed v0.3.5 baseline.

Date: 2026-06-09

## Objective

Make normalize replace and default source search indexing provable across the
trusted revision, chunk, FTS, source search, provider/output evidence, doctor,
artifact view, and retrieval regression surfaces.

Stage 2 preserves these rules:

```text
Revision = immutable source snapshot
Currentness = pointer, not mutation
Default source search = promoted current source revisions only
```

## Decisions Locked For Stage 2

- Schema migration is allowed for source FTS lineage companion tables.
- `chunks_fts` schema remains unchanged.
- Stage 2 implements lineage for `source_fts`; embedding/vector lineage is
  reserved by `index_kind` but not required.
- Do not backfill synthetic successful index builds during migration.
- Upgraded historical FTS rows without lineage surface as doctor warnings until
  a real rebuild creates lineage.
- Normalize replace has strong trusted-state atomicity: failures must leave the
  previous current revision, current chunks, FTS rows, and source search usable.
- Public output service APIs remain unchanged. Internal workflow helpers may be
  extracted only to improve locality and testability.
- Small deterministic retrieval regression is a PR CI blocker; larger dogfood
  corpus coverage remains scheduled, manual, or formal-release work.
- Agent-visible artifact views must not return local absolute vault paths,
  provider cache paths, `file://`, provider URIs, or raw trace bodies beyond
  bounded summaries.

- `src/indbase_core/provider_runs.py`
- `src/indbase_core/artifacts/`
- `tests/test_normalize_replace_regression.py`

Implementation tasks:

- Add failing regression tests before restructuring.
- Cover successful normalize replace from old current revision to new current
  revision.
- Prove previous revision and chunks remain durable.
- Prove previous chunks become `is_current = 0`.
- Prove new chunks become `is_current = 1`.
- Prove old FTS rows are deleted or excluded and source search returns only
  the new current revision.
- Prove `output_runs.created_revision_id`, adopted provider run, copied
  provider evidence, locator mappings, task status, errors, and review items
  are internally consistent.
- Prove FTS metadata is preserved for title, category, and trusted formal tags
  on the new current FTS rows.

Tests and gates:

```powershell

```

## Slice 2: Normalize Failure Atomicity

Implementation files expected:

- `src/indbase_core/output_service.py`
- `src/indbase_core/revisions.py`
- `src/indbase_core/chunker.py`
- `src/indbase_core/indexer.py`
- focused failure tests under `tests/`

Implementation tasks:

- Add failure-path tests for transition/provider failure, evidence adoption
  failure, chunking failure, and FTS/index lineage failure.
- Ensure failures do not move `documents.current_revision_id` to a half-finished
  revision.
- Ensure previous current chunks and FTS rows remain searchable after failure.
- Ensure any new revision written before failure is not current and is marked
  `never_promoted` or remains traceable through output/provider failure
  evidence.
- Retain provider/output failure evidence as visible diagnostic state.
- Extract minimal internal helpers only after tests define the invariants.

Tests and gates:


## Slice 3: Source FTS Lineage Schema And Writer

Implementation files expected:

- `src/indbase_core/migrations/0014_source_fts_lineage.sql`
- `src/indbase_core/indexer.py`
- `src/indbase_core/db.py` if migration loading needs adjustment
- `tests/test_db.py`
- `tests/test_indexer.py`

Schema expectations:

- `index_builds`
- `index_build_entries`
- `index_kind = source_fts` for Stage 2 writes
- build statuses: `running`, `succeeded`, `failed`
- entry statuses: `indexed`, `skipped`, `failed`

Implementation tasks:

- Add the migration without modifying `chunks_fts`.
- Create one source FTS build per indexer call.
- `rebuild_fts_index` creates a vault-level build.
- `reindex_document_fts` creates a doc-level build.
- Metadata-only FTS refreshes also create lineage builds with
  `metadata_refresh` trigger metadata.
- Store per-chunk lineage with `doc_id`, `revision_id`, `chunk_id`, and
  `index_build_id`.
- Do not create synthetic verified builds for existing rows during migration.

Tests and gates:

```powershell

```

## Slice 4: Doctor Drift Detection

Implementation files expected:

- `src/indbase_core/doctor.py`
- `tests/test_doctor.py`
- `tests/test_indexer.py`

Implementation tasks:

- Extend doctor checks so current chunks, FTS rows, current revision pointers,
  and source FTS lineage agree.
- Report errors for trusted current/search breakage:
  current chunks missing from FTS, FTS rows pointing to missing records,
  FTS rows pointing to non-current revisions, current documents without current
  chunks, and complete builds whose entries do not match current chunks.
- Report warnings for upgraded historical FTS rows without lineage and
  non-current old lineage that does not affect current source search.
- Report info for empty vaults and last successful source FTS build summaries.
- Add focused archive/restore interaction tests so archived historical rows do
  not become false current-drift errors.

Tests and gates:


## Do Not Touch

- Do not rewrite retrieval ranking.
- Do not add `indb ask`, generated answers, summaries, claims, cards, or LLM
  judges.
- Do not physically delete old revisions or chunks in normal workflows.
- Do not change consoler protocol/runtime/store/schema files from this
  repository.
- Do not make embedding/vector lineage mandatory in Stage 2.
- Do not modify `chunks_fts` schema.

## Done Means For Stage 2

- Normalize replace success and failure paths are covered by focused regression
  tests.
- Source FTS lineage exists for new rebuild, reindex-document, and normalize
  replace indexing paths.
- Doctor distinguishes current/search corruption errors from historical
  lineage warnings.
- Agent-visible artifact views do not leak absolute local paths or provider
  cache details.
- Deterministic retrieval regression gate blocks key query degradation.
- `scripts/v035_stability_hardening_gate.py` passes.
- Closeout includes CI evidence plus one dogfood smoke record or an explicit
  real-corpus waiver.
